## 1. ゴール

**どの言語の投稿でも、警告すべき投稿を見逃さず（最優先）、誤検知を減らし、費用を抑えて判定できる仕組み**を、Amazon Bedrock 上で作り、ベースラインと同じデータ・指標で効果を示す。

- 必須の課題 1（誤検知）と課題 2（言語による精度差）に重点を置く
- 「作った」で終わらせず、**言語別の改善前後の比較**で効果を自ら確かめて報告する
- 研究室の本体に取り込みやすい形（既存の構成・テストと整合）で `lambda/` に実装する

## 4. 重点を置く課題と仮説

### 4.1 重点の理由

- 運営は「見逃し」を最も嫌う（誤検知は目で除けるが、見逃しには気づけない）→ **再現率を守ることを制約、誤検知の削減を目的**とする
- Bedrock（Nova）への差し替えだけで精度が下がることが分かっている → まず**差し替えで落ちた分を言語別に特定**する
- 同じシナリオの 6 言語対訳なので、**言語だけが違う条件**で差を比べられる → 言語差の原因を切り分けやすい

### 4.2 改善候補（ベースラインの誤り分析で絞り込む）

| # | 候補 | 効くと考える誤り | 費用・時間への影響 |
|---|---|---|---|
| 1 | プロンプトの多言語化（判断方針を「言語に依らない」形に書き直し、各言語の典型表現を例示） | 英語・スワヒリ語などで勧誘・出会い目的を見落とす | 小 |
| 2 | 構造化出力の強制（Converse API の tool use で `decision`・`candidates` を enum で固定） | JSON 崩れ・存在しない条文 ID | 小 |
| 3 | 投稿を「データ」として区切る（区切り記号・役割の分離・指示に従わない旨の明記） | プロンプトインジェクション（O-3） | 小 |
| 4 | 2 段判定：Micro で高再現率のふるい分け → 「warn」だけ Lite で確認 | 誤検知（S 系の紛らわしい投稿） | 中（多くは 1 回で終わる） |
| 5 | 正規化：日本語・英語以外は英語へ翻訳（または要約）してから判定 | 低資源言語（sw・ar）の取りこぼし | 大（呼び出し 2 回） |
| 6 | 自己一貫性：境界の投稿だけ複数回判定して多数決（どれかが warn なら warn） | 判定の揺れ・境界事例の見逃し | 中 |
| 7 | 条文の絞り込み：多言語埋め込み（Titan / Cohere）で候補条文を検索 | 条文の付け方の揺れ（課題 4）、入力トークンの削減（課題 3） | 小〜中 |

> 方針：まず 1〜3（安く効く）を当て、残った誤りの種類に応じて 4〜7 を足す。**データに合わせた個別ルール（特定の言い回しの列挙など）は入れない**。

## 5. 目標水準（暫定。ベースライン計測後に確定）

| 観点 | 指標 | 暫定目標 | 根拠 |
|---|---|---|---|
| 取りこぼし（最優先） | 再現率・取りこぼし件数 | **Bedrock 版ベースライン以下の件数**（必達）。全体の再現率は OpenAI 版 0.941 以上を目指す | 発注書 M-4・8 章「見逃しを増やさない」。運営の運用（見逃しは気づけない） |
| 誤検知 | 適合率・誤検知件数・通知件数 | 誤検知件数を Bedrock 版ベースラインから **30% 以上削減**、適合率は OpenAI 版 0.750 以上 | 現状「通知の約 4 割が対応不要」＝適合率 0.6 前後の運用感。確認の手間を半分近くに減らす水準 |
| 言語間の差 | 言語別の再現率・適合率の最大−最小 | 再現率の差 **0.10 以内**、すべての言語で再現率 0.90 以上 | 対訳データなので内容は同じ。差は言語の扱いの差とみなせる。1 言語 25 件の警告すべき投稿で 1 件 = 0.04 の揺れを考慮 |
| 安定性 | 3 回判定の一致率 | **95% 以上** | 同じ投稿に違う判定が出ると運用の信頼を損なう |
| 費用 | 1 投稿あたりの費用・月額試算 | OpenAI 版 **$0.000475 以下** | 発注書の参考値。導入先が増えても費用を抑える（課題 3） |
| 時間 | 判定時間の中央値・p95 | p95 **3 秒以内**（目標）／ 10 秒以内（上限） | Lambda の時間制限・Slack への応答（ISS-03）を踏まえた運用上の上限 |
| 条文（O-2） | 条文の正解率・同一シナリオ内の一致率 | ベースラインより改善 | 課題 4 |

> 1 件で率が大きく動くので、**率と件数を必ず併記**する。数値は 3 回の平均と範囲で示す。

## 6. 評価設計と過学習対策

1. **シナリオ単位で分割**：同じシナリオの対訳が dev と test に分かれると答えが漏れるため、`scenario_id` 単位で分ける
   - dev（改善の試行に使う）：58 シナリオのうち約 60%（W/S・難しさの区分で層化、乱数の種を固定）
   - test（判断が固まってから 1 回だけ見る）：残り約 40% ＋ 言語混在 6 件
   - 分割は ID の一覧だけをリポジトリに置く（本文は置かない）
2. **全件でも報告**：OpenAI 版の参考値は 354 件全件の値なので、比較のため全件の結果も示す
3. **ホールドアウト**：`PJT04_追加データ.json`（16 件）と、自作データ（O-1）は最後まで見ない
4. **自作データ（O-1）**：提供データに無い言語（例：韓国語・スペイン語・ベトナム語・ポルトガル語）と種類（例：絵文字・URL 短縮・全角/半角混在・スレッド返信の文脈）を、架空の投稿で 40〜60 件。正解は `judge_decision.txt`・`article_guide.txt` の方針に従って付け、根拠を `note` に書く
5. **同じ条件**：モデル ID・温度・プロンプトのコミット・データの版・回数（3 回）を結果と一緒に記録する

## 7. 実装の設計（案）

```text
ViolationDetector(detection_mode="bedrock")
  ├─ BedrockJudge（boto3 bedrock-runtime / Converse API）
  │    ├─ 段 1: warn / safe と候補条文（tool use で JSON を強制、条文 ID は enum）
  │    └─ 段 2: warn のときだけ候補から 1 条文を選ぶ（judge_article.txt）
  ├─ 再試行: botocore Config(retries={"mode": "adaptive"}) ＋ 接続・読み取りのタイムアウト
  └─ 失敗時: DetectionResult(status="undetermined") → 「判定できなかった」として通知（O-4）
```

- 設定は環境変数（`DETECTION_MODE=bedrock`、`BEDROCK_MODEL_ID`、`BEDROCK_REGION`）。キーは持たず IAM ロールで呼ぶ
- CDK（`infra/stacks/infra_stack.py`）に `bedrock:InvokeModel` / `bedrock:Converse` の権限と環境変数を追加
- 評価側は `harness.py` に Bedrock のクライアント・`MODELS`・`PRICES`・トークン数と時間の記録を追加（本番コードをそのまま呼ぶ形は維持）
- テスト：`tests/unit/test_violation_detector.py` に Bedrock の正常系・JSON 崩れ・未知の条文 ID・例外・スロットリングを追加（boto3 は `pytest-mock` でモック）

## 9. 進め方のルール

- **コミット**：1 目的 1 コミット・動く状態で区切る・作業日は必ず push。メッセージは「何を変えたか」が分かる日本語で書く（例：「経路 B を Bedrock（Nova Lite）で動くように差し替え」）
- **ブランチ**：`feat/bedrock-baseline` → `feat/improve-*` → `docs/final-report` のように目的ごとに分け、PR で `main` に入れる（PR は自分のフォーク内）
- **評価の記録**：試した案ごとに「プロンプトのコミット・モデル・データ・結果（summary.csv）」を `docs/purchase_order/experiments/`（本文を含まない集計のみ）に残す
- **費用**：評価は先頭 5 件のスモーク → dev → 全件の順で回す。全件 × 3 回は 1 案につき 1 回まで
- **AI コーディング**：差分を必ず読んでからコミットする。講座の AWS 環境はコーディング支援には使わない
