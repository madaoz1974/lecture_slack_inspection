## ガイドの読み方

各ガイドは同じ構成です。

| 見出し | 内容 |
|---|---|
| ゴール | このガイドを終えると何ができているか |
| 前提 | 先に終わっているべきガイド・用意するもの |
| 手順 | 番号順に実行する。コマンドとコードはそのまま貼れる形で書いてある |
| ✅ 確認 | その手順が正しく済んだかを確かめる方法。**通らなければ次に進まない** |
| 💾 コミット | ここで 1 コミットする、という区切りとメッセージの例 |
| ⚠️ つまずきやすい点 | 先回りした注意 |
| 完了の条件 | ガイドの最後のチェックリスト。全部埋まったら次のガイドへ |

コマンドは、特に断りがなければ**リポジトリの直下**（`lecture_slack_inspection/`）で実行します。
コードの例は、このガイドを書いた時点（2026-11-24、コミット `9ecb72a`）のコードに合わせてあります。行の位置がずれていたら、関数名で探してください。

作成時の確認：ガイド 02・03・05・06・07・08 のコードは、一時的な作業ツリーに順に当て、`pytest tests/` が 170 → 184（02）→ 194（05）→ 204 passed（06）になることと、評価のスクリプト（分割・集計・比較・写し込みの確認・CI の offline の確認）が動くことを確かめています。Bedrock の呼び出しは偽の応答で確かめました。**実際の AWS の呼び出し・CDK（`cdk synth`/`deploy`）・GitHub Actions の実行は確かめていません**。それらの手順で食い違いがあれば、実物に合わせて直してください。

## 全体を通したルール（計画書 9 章の再掲）

1. **1 目的 1 コミット**。動く状態（テストが通る状態）で区切り、作業した日は必ず push する
2. ブランチは目的ごとに切る（`feat/bedrock-client` など）。`develop` へ PR で入れる。PR を作ると `pytest` の CI（`.github/workflows/test_lambda.yml`）が走る
3. **commit してはいけないもの**：API キー・AWS の認証情報、発注書 PDF、提供データの本文、評価結果の JSON（`evals/promptfoo/output/`）。集計（件数と率）だけは `docs/purchase_order/experiments/` に残してよい
4. 評価は **スモーク（5 件）→ dev → 全件** の順に広げる。全件 × 3 回は 1 案につき 1 回まで（費用と時間の節約）
5. 試したことは、効かなかった案も含めて [実験の記録](../experiments/README.md) に残す。説明資料の「考察」の材料になる
